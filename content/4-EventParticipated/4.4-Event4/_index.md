# FCAJ - Agentic AI Build Week

### Event Objectives

- Hear how Build Week teams turned a business idea into an Agentic AI prototype.
- Observe the AWS architecture, service choices and trade-offs behind their solutions.
- Learn from the teams' way of planning, dividing work and handling problems under time pressure.

### Speakers

- Representatives from **One Team**, **Plan V**, **3KA**, **Dream AI Team** and **Six Pillar Team**
- An international guest speaker for the opening session

### Key Highlights

#### Opening Session

The opening speaker talked about the fast changes in AI and shared a personal technology journey. The point I remembered was that curiosity and the habit of learning are still important even when tools change quickly.

#### Sharing Experiences from Build Week

The teams did not only show their final products. They explained the original problem, how the idea changed, the AWS services selected, technical issues and what they would improve. The examples included an AI-assisted self-service food kiosk and a finance-related customer interaction solution.

#### Cloud Architecture Demonstrations

The diagrams showed combinations of Amazon Bedrock and AgentCore for agent reasoning, API Gateway and Lambda for APIs, SQS for asynchronous work, and S3 or DynamoDB for storage. Some teams also used OpenSearch, ECS, Fargate, ECR, CloudFront and ALB. IAM, KMS, WAF, CloudWatch, CloudTrail, GuardDuty and Secrets Manager covered the operational and security side.

### Key Takeaways

- An Agentic AI product needs more than a model; it also needs APIs, data, queues, deployment and monitoring.
- A simple architecture that can be operated is often more useful than an overly complicated design.
- Time limits make task prioritization, communication and quick feedback especially important.

### Applying to Work

The session relates to my expense management project because it also uses S3, SQS, AI APIs, containers and AWS networking. I can apply the teams' approach by separating the first usable flow from optional features and checking the system from upload to final result.

### Event Experience

I found the event more useful than a normal technology introduction because the teams openly described problems they faced. Seeing both successful decisions and limitations made the development process feel closer to reality.

### Lessons Learned

I learned to think about the whole product instead of only one API or AI prompt. A project needs clear scope, a workable architecture, shared task ownership and repeated testing to move forward.
